# 五项验收分析

## 1. 提示词模板是否进入模型请求

证据：`验收证据/01_应用提示词对照_可控LLM.json`。

同一问题分别通过通用对话和课程知识库问答应用执行。两次 `llm_call_logs.request_json.messages[0]` 是不同的 system message，并包含各自应用名、班级名和知识策略。应用表保存 Prompt 副本；测试修改一个应用后，另一个应用内容保持不变。日志只记录实际发送字段，包括 model、messages、temperature、max_tokens 与 stream；未发送的 tools 不会被补写。

结论：在可控 LLM 链路中验证通过。真实外部课程 LLM 网关未运行。

## 2. 是否传递整个知识库

证据：`验收证据/02_检索切片证据_可控LLM.json`。

SSE meta 记录 `total_chunks`、`hit_chunk_ids`、mode 和 top_k；模型请求 user message 只出现命中的 evidence 摘录及真实 chunk 元数据，不包含整库正文。通用应用的 meta 明确为 `mode=disabled`，不会悄悄检索。启用检索但无命中时沿用固定“资料中未找到相关内容”，不调用 LLM、不生成 citation。

结论：实际宿主请求只传 Top-K 选中切片，不传整库。

## 3. Skill 是否完整进入模型请求

证据：`验收证据/03_Skill路由与注入_可控LLM.json`。

证据同时保存候选 Skill、关键词命中、选中 Skill、注入 SHA-256 和实际 LLM request。学习辅导问题命中 `solving_guidance` 后，system message 含 `Skill: solving_guidance` 及数据库中的完整指令内容。禁用、未绑定或未命中 Skill 时路由结果为空，system message 不附加其内容。

结论：Skill 不只是界面开关，完整内容确实进入实际请求。

## 4. Skill 执行逻辑

`solving_guidance` 通过“应用绑定 → 启用过滤 → 关键词匹配 → 优先级排序 → 单 Skill 选择 → system 注入”执行；`course_tool_assistant` 在同样路由后进一步产生获授权工具候选集。每轮最多选择一个 Skill。上传 Markdown 中即使含 Python 代码块也只保存为文本，不解释为执行了其中程序。

Skill route 日志保存候选、命中关键词、优先级、选择原因和注入哈希。MCP Skill 还可关联 `tool_name@server_name`，但运行期会再次检查服务器连接和发现清单。

结论：本项目中的 Skill 执行是确定性路由、指令注入和可选 MCP 编排，不是执行 Skill 文件中的任意代码。

## 5. MCP 接入时的 LLM 参数

证据：`验收证据/04_MCP完整调用链_真实MCP_可控LLM.json`。

该证据包含：真实官方 MCP SDK 的 tools/list 结果；实际发送给可控 LLM 的 OpenAI function 声明；返回的 tool_calls；宿主解析后的工具名与参数；真实 MCP tools/call 返回；下一轮 request 中 role=tool 的消息；最终响应和 tool_call SSE。

模型请求只包含 `course_tool_assistant` 当前绑定的 `lookup_course_glossary@course-tools`，没有把同服务器未授权的 `formula_hint` 一并声明。令牌从 `token_env_key` 指向的环境变量读取，只用于 MCP HTTP Authorization；证据、LLM request/response 和数据库追踪均不含令牌。

结论：真实 MCP 传输与工具执行链已验证；产生 tool_calls 的 LLM 是可控假客户端，不冒充真实课程模型。
